Что именно придётся добавить
1) Пользователи + авторизация
Хранение пользователей (SQLite/Postgres): email/логин, хэш пароля (bcrypt/argon2), статус, роли.
Сессии/JWT (лучше: cookie‑session для UI).
Middleware/Dependencies на FastAPI для защиты /api/* и страниц.
Оценка: 1–3 дня.
2) Регистрация “по приглашению”
Таблица invites: токен, роль по умолчанию, срок действия, “использован/нет”.
Админ‑эндпоинт “создать приглашение”, UI или CLI.
Оценка: 0.5–1.5 дня.
3) Индивидуальные параметры пользователя
Таблица user_settings (JSON) + схема (например: пороги уведомлений, список портфелей по умолчанию, скрытые секции, режимы анализа и т.п.).
API: get/update текущих настроек.
Оценка: 1–2 дня.
4) Ролевая модель + скрытие кнопок
Роли минимум: user/admin (в перспективе: manager, viewer).
На бэкенде: реальные запреты (не только скрыть кнопку) на эндпоинты:
/scheduler/run-now, настройки мониторинга/конфига, управление пользователями.
На фронте: скрытие/блокировка кнопок по me.role.
Оценка: 1–2 дня.
5) Планировщик/журнал с ролями
Журнал уже есть, но если “с ролями”:
кто запускал (user_id), откуда (manual/scheduled), параметры запуска, результат.
ограничение просмотра: user видит своё, admin — всё.
Если “планировщик” управляемый через UI: права на включение/изменение расписания.
Оценка: 1–3 дня.
Итого по времени (оценка)
MVP (user/admin + invite + user_settings + защита эндпоинтов + UI скрытие): 5–10 рабочих дней
Production‑уровень (логирование действий, audit trail, rate limiting, reset password, тесты, миграции Alembic, безопасные куки, CSRF): 2–4 недели
Что самое “муторное”
Безопасность и эксплуатация: куки/CSRF, хранение секретов, миграции БД, восстановление доступа, аудит действий.
Перенос текущего “пароля на весь дашборд” в полноценную модель без поломки UX.
